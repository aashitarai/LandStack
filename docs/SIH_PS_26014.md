# SIH Problem Statement 26014 — reference

Source: `SIH PS.pdf` provided by the user. This is the actual scope we're building toward now — supersedes the earlier "real-data-only Maharashtra prototype" framing for anything the PS explicitly asks for. Full detail preserved here so it doesn't need re-reading the PDF.

## The core pitch

"LandStack is an interoperable, parcel-centric intelligence layer that connects fragmented land governance systems through a common ULPIN-based framework."

Central flow: **GIS Map → Select Parcel → ULPIN → Unified Parcel Profile → Cross-department verification → AI anomaly detection → Satellite/change analysis → Property risk score → Government workflow → Governance analytics**

## Key thing that changes our approach

**The PS explicitly expects mock/synthetic departmental data.** Real government API integration is not required or expected at prototype stage — "the adapters can use mock JSON/CSV datasets," "Use mock/sample departmental datasets." This means our honesty-labeled DEMO layer approach was directionally correct — we now build it out fully across every department the PS lists, clearly labeled, structured so real APIs could later replace the mocks.

## Roles (RBAC)

- **Citizen**: search/select parcels, view permitted info, unified profile, ownership/registration/land-use/tax/restrictions, run due-diligence/risk check, submit + track service requests
- **Government Officer**: everything above + view anomalies, satellite alerts, risk heatmap, review flagged parcels, initiate/assign/update verification workflows, view audit history
- **Administrator**: manage users/roles, manage datasets/departments, system-wide analytics, API/integration status, audit logs

## Common parcel schema (minimum fields per PS)

- **Parcel**: ulpin, geometry, state, district, taluka, village, surveyNumber, area, landUse
- **Owner**: ownerId, name, ownershipType, share
- **Registration**: registrationId, ulpin, transactionType, date, status
- **Encumbrance**: encumbranceId, ulpin, type, institution, amount, status
- **BuildingPermission**: permissionId, ulpin, status, approvedArea, date
- **Tax**: taxId, ulpin, status, outstandingAmount
- **Restriction**: restrictionId, ulpin, type, status
- **Utility**: utilityId, ulpin, type, status

## State Adapter Framework — the named USP

Demonstrate with 3-5 states with genuinely different field names, transformed into the common schema via configuration (not per-state hardcoded logic):

- **Maharashtra**: survey_no, gat_no, khata_no, 7/12 details, holder_name, extent, classification
- **Tamil Nadu**: survey_number, sub_division_number, patta_number, chitta, owner, area, land_type
- **Karnataka**: survey_number, hissa, RTC/Pahani details, owner_name, extent, land_classification
- (Optional) Uttar Pradesh: khasra_number, khata_number, area, khatedar, land_type

Needs a small State Adapter Management UI: pick a state, see source schema, see field mappings, see resulting common schema, see validation/integration status.

## AI / intelligence — main differentiators

1. **Anomaly detection**: compare the same fact across departments (owner, area, land-use, status), flag mismatches with severity + confidence + explanation + recommended action. Never claim fraud — "Potential inconsistency detected — human verification required."
2. **Satellite/change detection**: timeline per parcel (e.g. 2023 Agricultural → 2025 Construction detected → 2026 Built-up), simulated imagery acceptable, "Action: Send for verification," never claims a legal violation.
3. **Property risk score**: explainable 0-100, built from ownership consistency / registration / mortgage / tax / land-use / approvals / restrictions / anomalies, always with reasons and the disclaimer "This is an informational due-diligence indicator and does not constitute a legal title certificate."

## Government dashboard

Total parcels, anomalies, land-use changes, pending verification, tax issues, GIS risk heatmap, charts (anomalies by district, changes over time, workload), district → area → parcel drill-down.

## Workflow / service requests

Example chain: Citizen submitted → Land Records Verification → Registration Verification → Planning Verification → Final Review → Resolved. Officer updates status; citizen sees progress with checkmarks/timestamps.

## Audit trail

Every sensitive change logged: officer, department, timestamp, field, previous value, new value, reason.

## Data provenance

Every displayed fact shows source department + last-updated date.

## Demo data

30-50 synthetic parcels, deliberately varied:
- Parcel A: everything verified, low risk
- Parcel B: area mismatch → anomaly
- Parcel C: owner mismatch → high-priority verification
- Parcel D: agricultural → construction detected → satellite alert
- Parcel E: active mortgage + tax dues → moderate/high risk
- Parcel F: pending building permission → workflow example

One **hero parcel** should walk through the entire flow end-to-end for the demo.

## Priority order if time-limited

**P0 (must work)**: GIS parcel map, ULPIN, parcel selection, unified parcel profile, common schema, mock departmental APIs, citizen/government RBAC.

**P1 (differentiators)**: AI anomaly detection, property risk indicator, satellite/change detection, state adapter layer, government risk dashboard.

**P2 (supporting)**: workflow tracking, audit trail, data provenance, advanced/natural-language search, mobile optimization.

## Tech stack called for

React + TypeScript frontend (PS says React — we're on Next.js/React, compatible), Python FastAPI backend, PostgreSQL + PostGIS, GeoJSON for parcel exchange, REST + JWT/RBAC, Docker for local deployment. OGC API – Features concepts encouraged for the geospatial API.

## How this reconciles with what we already built

Our real-data work (real OSM parcel geometry for Pune/Kharghar/Panvel, real Bhu-Naksha single-lookup government records, statewide search, land-system classifier) becomes **one genuinely real input** feeding into the ULPIN-centric platform — not thrown away. Everything the PS explicitly wants as mock (multi-department records, anomalies, satellite timeline, risk score, workflow, audit) gets built as clearly-labeled synthetic/demo data per the PS's own instructions, structured so real APIs could swap in later.
